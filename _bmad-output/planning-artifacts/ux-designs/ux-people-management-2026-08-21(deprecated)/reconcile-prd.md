# Reconciliation: DESIGN.md / EXPERIENCE.md vs prd.md / access-model.md

**Checked:** all 55 FRs (PRD §5) against EXPERIENCE.md's IA table, Component Patterns, State Patterns, Interaction Primitives, and Key Flows for a corresponding UX surface; UJ-1/UJ-2 fidelity (persona, entry state, core beats, access-model claims) against PRD §3.3; glossary terminology (S1–S16, role names, Shared Link, Colleague, etc.) against PRD §4 verbatim; every access-model behavioral claim in both spines against `access-model.md`'s actual matrix and rules; and the spines for invented functional behavior with no PRD basis. UX-authored additions explicitly exempted per task scope (IA structure, component/state naming, UJ-3, visual tokens, responsive behavior) are not flagged below even where they go beyond the PRD's text, since that's UX's own legitimate authoring job.

## Findings

- **Feedback feature (FR-44, FR-45, FR-46 / S8) has zero UX surface.** PRD §5.11 defines three FRs: recording feedback with a management-only/shared-with-employee flag, viewing records chronologically with **side-by-side two-period comparison** (a distinctive interaction with an explicit empty-column rule for FR-45), and a request-feedback-from-named-colleagues flow built on Form Campaigns. None of this appears anywhere in EXPERIENCE.md — not in the IA table, not in Component Patterns, not in State Patterns, not in Key Flows. The generic "Profile Section Card" pattern (one card per section, RW = inline edit) cannot stand in for FR-45's period-comparison view, which is a categorically different UI shape from a single editable card. Glossary term "Feedback record" (PRD §4) is correspondingly never used in either spine. **Severity: critical.**

- **FR-11 (Export to `.xlsx`) has zero UX surface.** All Employees / Data Table gets extensive treatment in EXPERIENCE.md (sort, filter, inline edit, saved views as tabs, sticky header, column filters) but "export" is never mentioned once, in the IA table, Component Patterns, or Interaction Primitives. **Severity: moderate.**

- **FR-6's generation/management side (manager creates/configures/revokes a Shared Link) has no UX surface — only the consumption side is covered.** EXPERIENCE.md shows the Access Scope Chip *displaying* "Shared link — expires in 4h" and the Resourcing Candidate Card *embedding* a shared-link view (UJ-2), but there is no component, IA entry, or flow for the actual manager-facing action: choosing which `cfg` sections to include, setting/adjusting the expiry, or revoking the link before expiry — all explicitly testable FR-6 behaviors. **Severity: moderate.**

- **EXPERIENCE.md's Foundation section asserts the Shared Link view is "unauthenticated," which is unsupported by the PRD/access-model.md and contradicts the spine's own UJ-2 notes.** Neither `prd.md` nor `access-model.md` states an authentication requirement for Shared Link consumption — access-model.md lists "Shared link" simply as one of several resolvable audiences, silent on auth state. PRD's UJ-2 has Marcus, an already-authenticated DM, consuming the shared-link-scoped view of the candidate profile; EXPERIENCE.md's own UJ-2 notes reinforce this — the Resourcing Candidate Card "embeds the Shared Link view inline... rather than navigating him away from the request," i.e., inside his authenticated session. Yet the Foundation section and the IA table (Shared Link view = "External URL (no nav entry)") frame it as a separate unauthenticated, no-nav route. These two framings of the same surface don't reconcile, and the "unauthenticated" claim in particular reads as an invented functional detail rather than a UX styling choice. **Severity: moderate.**

- **Career Timeline (FR-28/FR-29/FR-30, S9) gets no dedicated Component or State Pattern**, unlike Risk, CDS, Mentorship, and Campaigns, which each get explicit named components/flows. In particular, FR-30's manual-vs-system conflict rule ("a manually edited event is never silently overwritten... the system write is skipped and logged") has no UI/messaging treatment anywhere — there's no indication of how or whether a user is ever told a system update was skipped. Glossary term "Timeline event" (PRD §4) is never used in either spine. Weaker than the Feedback gap since generic Profile Section Card editing plausibly covers basic add/edit, but the feature-specific behaviors are entirely unaddressed. **Severity: moderate.**

- **FR-4's dual-visibility-flag UI (visible-for-employee / visible-for-PM) is never specifically depicted.** UJ-1's UI notes mention S7's "inline 'Add note' affordance" but never describe the two independent off-by-default flag controls that FR-4 requires. **Severity: minor.**

- **FR-10's "shared with other managers" behavior has no affordance.** EXPERIENCE.md's Data Table row covers "saved views as tabs above the table" (creation/switching) but never depicts how a view gets shared with other managers, despite that being one of FR-10's stated behaviors. **Severity: minor.**

- **Access Scope Chip's enumerated states omit HR Admin.** EXPERIENCE.md's Component Patterns table lists "Manager line / PP / Colleague / Shared link" as the chip's possible states, but FR-1 explicitly names HR Admin as a sixth resolvable access role for profile viewing. Not a contradiction, just an incomplete enumeration. **Severity: minor.**

- **DESIGN.md's Section Gate description overgeneralizes who can see a gate.** The prose reads "a placeholder shown only to PP/Manager roles who could theoretically toggle a section's visibility" — but per `access-model.md`, PP has unconditional RW on S7 regardless of flags, and UM/DM ("UM, DM, and PP see all notes regardless of flags") likewise never hit the gate; only a PM does. The Do/Don't table's own worked example correctly narrows this to "the PM/S7 case," and EXPERIENCE.md's Component Patterns table correctly scopes the gate to "S7 only, PM viewer" — so the looser lead-in sentence in DESIGN.md is the one inaccurate spot. **Severity: minor.**

- **Internal inconsistency (not a PRD contradiction) between the two spine files on Access Scope Chip visibility on My Profile.** DESIGN.md's Do's/Don'ts table says "Show the Access Scope Chip on every profile view," while EXPERIENCE.md's Component Patterns table says "Never shown on My Profile." The Access Scope Chip itself is a legitimate UX invention (not in the PRD), so this isn't a PRD-fidelity issue, but the two documents disagree with each other on its behavior. **Severity: minor.**

- **FR-15 (upload photo/certificates) has only generic coverage.** File upload is a materially different interaction from the "inline edit" pattern EXPERIENCE.md describes for RW fields, but no upload-specific component or affordance is called out anywhere. **Severity: minor.**

## Not flagged (checked, found sound)

- **FR coverage:** all remaining ~48 of 55 FRs (access resolution, profile assembly, Colleague whitelist, functional roles/admin, directory/custom fields/inline-edit, self-service core, action items, risks/risk dashboard, resourcing, CDS core, mentorship, campaigns, dashboards, integrations) each have a clear corresponding IA entry, component, state pattern, or flow.
- **Journey fidelity:** UJ-1 and UJ-2's persona names, entry states, and core beats in EXPERIENCE.md's Key Flows match PRD §3.3 exactly (Daniela/PP Dashboard/risk counter/drill-through/S7 note/own note+action item; Marcus/resourcing request/Shared Link sections example S1+S4+S12 = Identity+Employment+CDS/external PeopleForce fallback). No behavioral claim in either UI note contradicts the PRD or access-model.md's "who sees what" rules — the S7/PP-unconditional-access detail in UJ-1 and the Shared-Link-scoped-sections detail in UJ-2 are both correctly stated.
- **Glossary consistency:** every term used in both spines (Manager line, PP, Colleague, Shared Link, HR Admin, Action item, Mentorship pair, CDS, IDP, and the UM/DM/PM/PP functional-role abbreviations) matches PRD §4 / access-model.md verbatim; no synonyms invented. ("Campaign" as shorthand for "Form Campaign" mirrors the PRD's own FR-level usage, not an invented term.)
- **Access-model fidelity (remaining claims):** "a `—` section is not rendered, not gated" — correct per access-model.md's legend and Rule 1/3. "The S7/PM case is the one documented exception" — correct, matches access-model.md verbatim. "Shared Link is always read-only" — correct, matches Rule 7. "Colleague mode auto-applies when the viewer has no elevated role" — correct, matches the Colleague definition (derived, never assigned/toggled).

## Verdict

Solid overall fidelity — FR coverage, journey accuracy, and glossary discipline are strong across the majority of the PRD's scope — but the Feedback feature (FR-44–46) is a genuine, unaddressed gap that should be closed before this spine is treated as complete, alongside the moderate gaps in export, Shared Link generation UI, the unsupported "unauthenticated" claim, and Career Timeline's missing treatment.
