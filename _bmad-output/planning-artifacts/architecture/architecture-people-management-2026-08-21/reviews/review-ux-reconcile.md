# UX Reconciliation Review — ARCHITECTURE-SPINE.md vs. DESIGN.md / EXPERIENCE.md

Checked: (1) AD-11's frontend-surfaces claim against EXPERIENCE.md's actual IA table; (2) whether Component Patterns entries with real backend data needs (Feedback Panel period-comparison, Shared Link Manager, Career Timeline's "system update skipped" indicator, Access Scope Chip) have a contract/provider counterpart in the spine; (3) whether the ERD supports the data shapes DESIGN.md's components imply (Trend Arrow's previous-value diff, Status Badge's completed state); (4) quiet requirements in either UX file with no seed anywhere in the AD structure. Scope excludes anything the SPEC/PRD/access-model/adversarial passes already covered (dependency direction, C1–C8 completeness, deployment, test architecture, caching, temporal data).

## 1. IA surface mapping (AD-11 vs. EXPERIENCE.md)

EXPERIENCE.md's IA table lists 11 surfaces: Dashboard, All Employees, Employee Profile, My Profile, Resourcing, Risk Dashboard, Campaigns, Mentorship Hub, Admin — Functional Roles, Admin — Custom Fields, Shared Link view.

AD-11's source-tree seed lists: `Dashboard, AllEmployees, EmployeeProfile, MyProfile, Resourcing, RiskDashboard, Campaigns, MentorshipHub, AdminRoles, AdminFields; SharedLinkView as its own unauthenticated-shell route` — 11 folders, 1:1 with the 11 IA rows by name. No surface is missing and none is invented.

One row's *treatment*, not its presence, is wrong — see the first gap below.

## Gaps

- **[CRITICAL]** AD-11's structural seed calls `SharedLinkView` "its own **unauthenticated**-shell route," but EXPERIENCE.md's Foundation section states the opposite as a deliberate (flagged-assumption) design decision: *"Every surface requires an authenticated session, **including Shared Link consumption** — in UJ-2, an already-authenticated DM consumes a shared-scoped view inline within his own session... `[ASSUMPTION: ...authenticated-consumption is assumed as the safer default...]`"*. UJ-2 itself narrates the shared link rendering *inline inside Marcus's own session* on the Resourcing Candidate Card, not as a standalone public page. Building `SharedLinkView` as an unauthenticated route (no session, no auth guard) contradicts this explicit UX decision and would require a materially different route/guard implementation (public token-auth vs. session-auth + token-scoped query) than what EXPERIENCE.md specifies.
  **Fix:** Change AD-11's seed to `SharedLinkView` as an authenticated route gated by the normal session guard, additionally scoped by the link token (validated server-side against `SharedLink`/`SharedLinkSection`), not a public/unauthenticated shell. If the intent really is to support account-less external recipients later, that's a scope change EXPERIENCE.md flags as unconfirmed — the spine should not silently resolve that open question in the opposite direction from the UX spine's stated default.

- **[CRITICAL]** EXPERIENCE.md's Career Timeline component (Component Patterns) requires: *"When a system-generated update is skipped because it would overwrite a manual edit in the same window, the manual entry gets a small info affordance ('A system update was skipped here — {date}') rather than the skip happening invisibly (per FR-30)."* This needs (a) conflict-detection logic in `integrations` (or wherever the system-sourced write originates) that recognizes a pending overwrite of a manual edit and suppresses it, and (b) a way to attach that skip fact to the *existing* manual `TimelineEvent` so the frontend can render the affordance on it. Neither exists anywhere in the spine: C4's `TimelineEventWriter` signature (`recordTimelineEvent(employeeId, type, effectiveDate, oldValue, newValue, source, authorId?)`) has no field for "a system update was skipped here," no skip-event type, and AD-7's Prisma Client Extension coupling (history-table write → automatic C4 call) says nothing about *not* writing when a manual edit conflicts. A frontend developer building the Career Timeline against EXPERIENCE.md would find no backend counterpart for this indicator at all.
  **Fix:** Extend C4/TimelineEvent's ratified shape (or add a small companion field, e.g. `skippedSystemUpdateAt` / a linked skip record) and state where the conflict-detection check lives (most naturally: the history-table write path in `integrations`, before the Prisma extension fires C4) as an explicit AD or a documented extension of AD-7.

- **[MODERATE]** DESIGN.md's Trend Arrow ("an *increasing* trend uses the destination level's own risk color... a *decreasing* trend uses `{colors.success}`") requires diffing the current risk level against the previous one. The spine's ERD has `Employee ||--o{ RiskRecord : has` and AD-3 mentions `risks: DashboardSummaryProvider` producing "risk counts," but nothing states whether trend direction is a backend-computed field on the risk `SectionDto`/`DashboardSummaryProvider` output, or whether the frontend is expected to fetch RiskRecord history and diff the two most recent entries itself. Given the architecture's own stated principle ("the frontend has no independent access logic to keep in sync") and that Risk Badge + Trend Arrow render identically on Profile, All Employees, and Risk Dashboard (three different data-fetch paths), leaving trend computation unspecified risks three independent, possibly-diverging frontend implementations of the same diff logic.
  **Fix:** Add a `trend: "up" | "down" | "flat"` (or `previousLevel`) field to the risk SectionProvider/DashboardSummaryProvider DTO shapes, computed once backend-side, so all three surfaces consume the same pre-computed value rather than re-deriving it.

- **[MODERATE]** EXPERIENCE.md's Shared Link Manager states S3/S7/S13 are "**structurally excluded**, not just unchecked" from the shareable-sections checkbox list — a deliberate, named business rule (these are presumably the most sensitive sections: compensation-adjacent, management notes, etc.). Nothing in the spine's AD structure, contracts, or ERD (`SharedLink ||--o{ SharedLinkSection : configures`) states or enforces this exclusion. As written, `SharedLinkSection` could reference any of S1–S16, and only a frontend checkbox-list omission would prevent sharing S3/S7/S13 — which is exactly the "client-side-only visibility filtering" pattern EXPERIENCE.md's own Interaction Primitives section explicitly bans ("any client-side-only visibility filtering... a section a viewer can't see must never be in the DOM to begin with").
  **Fix:** State the S3/S7/S13 exclusion as a backend-enforced invariant (e.g., part of `access` module's SharedLink-creation validation, or a constraint noted alongside AD-5's whitelist pattern), not left implicit.

- **[MINOR]** EXPERIENCE.md's Foundation states i18n is mandatory ("`react-i18next`, English only for now, but no hardcoded strings anywhere") as an existing frontend convention every new surface must follow. The spine restates several other "existing convention" disciplines explicitly (TanStack Query exclusivity, `LayoutContext` as the only cross-cutting UI state, Jest/Playwright conventions) in its Consistency Conventions table, but never mentions i18n anywhere — not in the Stack table, not in Consistency Conventions. Low risk since it's an existing pattern, but its absence is inconsistent with how carefully the spine otherwise restates inherited conventions it wants held onto.
  **Fix:** Add a one-line Consistency Conventions row (or fold into the "Naming"/"Frontend server state" rows) restating the i18n-key discipline for all new copy.

- **[MINOR]** DESIGN.md's Status Badge (Positive) and Overdue Indicator are used across four different entities — completed Action Item, completed IDP, ended Mentorship Pair (gated on recorded closing feedback per FR-37), and a fully-completed Campaign Completion Table row — each implying a clear "completed" boolean/state per entity. The spine's ERD doesn't enumerate these fields (only relationships: `Employee ||--o{ ActionItem`, `CDSRecord ||--o{ IDP`, `MentorshipPair}o--||Employee`, `FormCampaign ||--o{ CampaignRecipient`), and C6's `ActionItemCreation` signature covers creation params only, not the full read/complete shape. This is likely fine at spine altitude (field-level schema is a lower-altitude concern, unlike AD-6/AD-7 which get dedicated ADs because they have non-obvious modeling traps), but MentorshipPair specifically has a coupling worth naming: EXPERIENCE.md requires the positive badge to appear only once closing feedback is recorded, not merely when the pair is marked ended — i.e., "ended" and "has closing feedback" must not be modeled as independently settable, or the badge/feedback display could show one without the other.
  **Fix:** No spine-level change required; flag for the data-model/story-writing pass that MentorshipPair's "ended" state and its required closing-feedback text should be captured atomically (e.g., `endedAt` is only ever set alongside `closingFeedback`, never independently).

## Verdict

CONCERNS — two critical UX-to-architecture contradictions (Shared Link auth model, Career Timeline skip indicator) plus three lower-severity gaps; none blocks Finalize outright, but both criticals should be resolved before build starts on Resourcing (UJ-2) and Career Timeline (CAP-7) tracks.
