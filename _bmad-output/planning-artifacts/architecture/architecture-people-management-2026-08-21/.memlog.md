- (decision) contracts module holds only abstract tokens/interfaces (C1-C6), no logic — each owning feature module provides the concrete implementation bound to its token; consuming modules inject via the token and never import the owning module directly. Prevents circular module dependencies between e.g. access (consumes C4 Timeline Writer) and timeline (owns C4, consumes C1 AccessResolver).
- (decision) backend module map (13 SPEC capabilities -> Nest modules), ratifying interface-contracts.md's ownership: contracts (abstract tokens only, no logic) / auth (new — login, JWT, session) / access (CAP-1: C1 AccessResolver impl, profile assembly across S1-S16, functional roles+permissions, shared links; consumed by every other feature module) / directory (CAP-2: C2 FieldRegistry impl, employee list, custom fields, saved views, export) / action-items (CAP-4: C6 action-item-creation impl) / risks (CAP-5) / resourcing (CAP-6) / timeline (CAP-7: C4 Timeline Event Writer impl) / cds (CAP-8) / mentorship (CAP-9) / campaigns (CAP-10) / feedback (CAP-11) / dashboards (CAP-12, read-only composer over other modules' data) / integrations (CAP-13: C5 external-identity-mapping impl, timetracker+PeopleForce clients, C3 ProjectAssignment writer). CAP-3 Self-Service has no dedicated module — it's the access module's profile endpoints scoped to Self, consumed differently by the frontend, not a separate backend domain. Dependency direction: every feature module may depend on contracts and access; access may depend on contracts only; no feature module depends on another feature module directly except through a contract token.
- (decision) profile assembly vs. dependency-direction tension resolved via a Section Provider Registry: each section-owning module (risks, timeline, cds, mentorship, action-items, feedback, etc.) implements a `SectionProvider` contract (declared in contracts module: `getSection(employeeId): SectionDTO`) and registers it against its own section id; the access module's ProfileAssemblerService depends only on the abstract SectionProvider array (multi-injection via a DI token), never on the concrete feature modules. This lets profile assembly span all 16 sections without violating "no feature module depends on another feature module directly" — the dependency still only flows feature-module -> contracts.
- (event) self-check: AccessResolver (C1) must be called on EVERY section read across EVERY module (S1-S16, all owned by different modules) — the Section Provider Registry pattern is the mechanism that makes "called on every request touching profile-scoped data" (SPEC constraint) structurally enforced rather than each module remembering to call it independently: ProfileAssemblerService resolves access ONCE per request and only invokes the SectionProvider for sections the resolved role grants, so a provider is never even called for a section the viewer can't see (defense in depth beyond just filtering the response).
