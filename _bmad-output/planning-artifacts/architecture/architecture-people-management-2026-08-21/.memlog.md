- (decision) profile assembly vs. dependency-direction tension resolved via a Section Provider Registry: each section-owning module (risks, timeline, cds, mentorship, action-items, feedback, etc.) implements a `SectionProvider` contract (declared in contracts module: `getSection(employeeId): SectionDTO`) and registers it against its own section id; the access module's ProfileAssemblerService depends only on the abstract SectionProvider array (multi-injection via a DI token), never on the concrete feature modules. This lets profile assembly span all 16 sections without violating "no feature module depends on another feature module directly" — the dependency still only flows feature-module -> contracts.
