Access-First Blueprint

Why this document, why now

One idea does most of the work

Every other product decision in this platform is fairly ordinary CRUD — records, lists, dashboards. The one thing that isn't ordinary is that the same screen renders differently for every viewer, because every section of every profile carries its own access rule. That's not a feature bolted onto a normal app. It's the thing the whole backend is organized around.

Layered NestJS modules, one per capability, controller → service → Prisma — nothing exotic. What makes it hold together across three people building in parallel is a handful of rules about who may call whom, and one shared mechanism (below) that lets modules read each other's data without importing each other's code.

The mechanism

Provider Registry — read across modules, never import across modules

AD-1 says a feature module can never import another feature module directly. Good rule, obvious problem: assembling one employee profile means reading from thirteen different modules (risks, notes, timeline, CDS, feedback...). NestJS doesn't have Angular-style multi-providers that would solve this for free, so the mechanism is explicit: a tiny registry module uses DiscoveryService to find every class tagged @RegisterProvider(family, id) at boot, and index it. Nobody imports anybody — everybody registers with the registry.

AD-3 — three provider families share this exact mechanism: SectionProvider (profile assembly), FieldProvider (Directory's CDS-derived filters), DashboardSummaryProvider (Dashboards' aggregates). Same registry, same rule.

The part worth saying out loud in the room: access is resolved once per request, before any provider is called — a provider for a section the viewer isn't granted is never invoked at all. That's stronger than filtering the response afterward, and it's why a Colleague viewer's response can never accidentally contain a risk record: the risk provider was never asked.

Parallel delivery

Eight contracts, frozen before Wave 1

This is the actual mechanism behind "no developer waits on another." Each contract is a TypeScript abstract class in contracts — an injection token, not a promise. A track can build against a stub provider (fixed return value) from day one, and swap in the real implementation later with zero change to callers. Two of the eight didn't exist before this review round — real gaps, not paperwork.

The thirteen

Every rule, grouped by what it protects

Boundaries & contracts
AD-1Module dependency direction

Feature modules depend only on contracts and registry — never each other. Enforced by dependency-cruiser in CI, not just convention.

AD-2Contracts hold interfaces only

Zero logic, zero Prisma in contracts. Every HTTP-facing DTO must be plain-JSON-serializable — a Map stays in-process, never crosses the wire as-is.

AD-3Provider Registry

DiscoveryService-based registration for Section/Field/DashboardSummary providers. Collision = bootstrap failure. Missing registration = explicit "unavailable," never silent omission.

named the real NestJS mechanism
Access & security
AD-4No cache by default

AccessResolver re-resolves every request. If a cache is ever built, it must invalidate on every ProjectAssignment write — including a bare confirmed flip, not just row create/delete.

AD-5Whitelist is data, not a filter

Colleague resolves to a fixed section-grant map, same code path as any other role. Shared Link's S3/S7/S13 exclusion is enforced the same way — server-side, never a frontend checkbox omission.

AD-8Confidence state gates access

confirmed + confirmedAt on ProjectAssignment. Access requires both true and fresh — a sticky flag from before an outage ages out, it doesn't grant forever.

closed a stale-grant gap
AD-9Auth ≠ access

auth knows who you are. access knows what you can see. Neither knows the other's job — an SSO swap later touches one module, not the access model.

Data shape
AD-6Custom fields: typed columns, not new tables

One CustomFieldValue table, one populated column per row. Unused columns are NULL, never a sentinel. Rows are created lazily — a missing row is "unset."

AD-7Temporal fields are history tables

Grade/position/department/employment-type: one effective-dated table each, never a scalar-plus-audit-log. A Prisma extension fires the timeline event automatically — when a system update loses to a manual edit, C4's markSystemWriteSkipped annotates the manual entry with the skip affordance.

Frontend & delivery
AD-10Generated API types

openapi-typescript from the live Swagger spec, committed and CI-diffed. No hand-written parallel DTOs to drift.

AD-11Frontend pages mirror the UX spine's IA

One page folder per EXPERIENCE.md surface, not per backend module. Cross-capability flows (e.g. "request feedback") are frontend-orchestrated — modules never call each other to fake it.

AD-12Deployment

Single containerized deploy — docker-compose across backend, frontend, Postgres. One environment. No k8s, no staging tier, this iteration.

added — was only in the memlog
AD-13Test architecture

One parameterized access-matrix suite per section, driven straight off the matrix table. Lives next to the provider it verifies — not a separate test module.

added — SM-1 had no home

Not decided yet — on purpose

Deferred

Naming what's not pinned matters as much as what is — it's the difference between "we haven't gotten to it" and "go ahead and guess."

Cache implementation — the shape is constrained (AD-4), the build is deferred until NFR.2 testing shows a real bottleneck.
PeopleForce specifics — auth, endpoints, rate limits are CAP-13's own investigation; the outbound-link fallback means nothing blocks on it today.
Notifications & Analytics — good-to-have, no architectural seed until back in scope.
Horizontal scaling, staging tier, CI/CD pipeline choice — downstream of AD-12's single-container decision; revisit only if that changes.
Freshness-window value for AD-8 — the mechanism is fixed, the number waits on knowing the real sync interval.

Before Wave 1

Wave 0 checklist

→Freeze C1–C8 as TypeScript abstract classes in contracts, with stub providers, before any feature module starts real work.
→Stand up registry — the DiscoveryService plumbing — since three providers (Section/Field/DashboardSummary) all depend on it existing first.
→Wire the dependency-cruiser CI rule so AD-1 is enforced from commit one, not discovered in a PR review three weeks in.
→Land the four temporal history tables (AD-7) and the Prisma extension that couples them to the timeline — this is upstream of Career Timeline, Self-Service, and Directory all at once.
→Set up the parameterized access-matrix test scaffold (AD-13) against access-model.md before the first section provider ships, so every provider is tested the same way from its first commit.
→Build the pseudonymized seed-data tool (spec NFR.3) — every track needs realistic data from day one, not partway through.
