GOOD

On the seven-dimension quality rubric alone, this PRD is Excellent: every dimension is strong or adequate, and every issue the rubric walker found this session (a stale FR-range claim, a broken cross-reference, a self-contradictory Assumptions Index entry, a missed glossary term, seven FRs missing Consequences bullets) was fixed and verified against the file before this report was written.

The edge-case-hunter lens tells a different story, and it's the one that matters more before this feeds bmad-architecture. Walking every branch the access model, departure cascade, and resourcing lifecycle imply, it found 22 unhandled paths — several of which are not cosmetic gaps but direct violations of guarantees the PRD states elsewhere: FR-8 promises full profile access is "never revocable down to zero holders," but neither concurrent mutual revocation nor the sole holder's own departure is guarded against it. SM-6 promises a shared link "stops working" when the creator's relationship ends, but FR-63's departure cascade never mentions shared links at all. FR-31 promises headcount is "always accurate," but there is no un-approve path once a candidate is found ineligible. These are cheap to close now, in a requirements document, and expensive to discover mid-implementation of the access layer — this platform's stated primary quality attribute. That gap is why the grade is Good rather than Excellent.

Edge-case lens

22 unhandled paths found via exhaustive branch-walk of the access model, departure cascade, and resourcing lifecycle. Access-model precedence & self-reference (FR-1, FR-2, FR-7)
unresolved

No precedence rule for multi-role viewers

FR-1, FR-2
Nothing states what happens when a viewer resolves to two+ access roles (e.g. Project line and PP) for the same subject — only the S7 PM-flag case has an explicit rule.
Fix: state the resolution rule — e.g. section access is the union of every resolved role's grants, per section.
unresolved

Self-managed department loophole

FR-7
Nothing blocks setting a department's manager to a current member of that department — granting Reporting-line access to one's own profile, bypassing "risk never visible to self."
Fix: a department's manager may never be a current member of that department or a nested sub-department.
unresolved

Manager-chain cycle

FR-7
Two sequential legitimate edits (A manages B, then B manages A) can form a cycle with no stated guard, breaking the reporting-line transitive-closure walk.
Fix: reject a manager edit if the proposed manager is already a descendant of the employee in the reporting chain.
unresolved

Concurrent conflicting access-switch writes

FR-7, FR-9
Two actors writing different values to the same access-switch field concurrently has no stated resolution; the journal records outcomes, not conflicts.
Fix: reject the losing concurrent write with a conflict error rather than silently overwriting.
unresolved

Orphaned department on manager-field clear

FR-7
Clearing a department's-manager field directly (not via departure) isn't blocked, leaving members with no Reporting-line coverage until noticed.
Fix: block clearing a department's-manager field unless a replacement is designated in the same change.
Full profile access floor (FR-8)
unresolved

Concurrent mutual revocation drives holders to zero

FR-8
The last two holders each revoking the other at the same instant isn't guarded against — FR-8 states the invariant but not the write-time check.
Fix: re-check the current holder count at commit time and reject any revocation that would drop it to zero.
unresolved

Sole holder's own departure bypasses the floor

FR-8, FR-62, FR-63
FR-62's re-parenting gate covers management/PP relationships but never checks full-profile-access status; FR-63's cascade would revoke the last holder's grant regardless.
Fix: extend FR-62's blocking gate to require transferring full profile access first if the departing person is its sole holder.
Departure cascade completeness (FR-61–65)
unresolved

Shared links outlive their creator's departure

FR-63, SM-6
FR-63 never mentions shared links, so SM-6's own promise that a link "stops working when the creator's relationship ends" has no enforcing step for the departure case.
Fix: add "every shared link the departing employee created is revoked" to FR-63's cascade.
unresolved

Saved views become permanently frozen

FR-13, FR-63
A saved view is editable/deletable only by its creator; FR-63 never transfers or retires that ownership on departure.
Fix: on departure, saved-view edit/delete rights transfer to a current manager/PP, or the view is retired.
unresolved

Double-departure race on a shared mentorship pair

FR-43, FR-63
If both mentor and mentee depart on overlapping dates, nothing states the auto-close is idempotent against a pair already ended.
Fix: state that departure-triggered pair auto-closure is a no-op against an already-ended pair.
unresolved

Concurrent cancellation race on action items

FR-22, FR-63
A manual cancellation and a departure-triggered auto-cancellation against the same item, arriving concurrently, has no stated ordering rule.
Fix: a cancellation write against an already-cancelled item is a no-op regardless of which path arrives second.
unresolved

Shared-link scope doesn't re-clamp to creator's narrowing access

FR-6
If the creator's own access narrows short of full departure (e.g. loses a project), nothing states the link's exposed sections shrink to match.
Fix: a shared link's exposed sections re-clamp, on every view, to whatever access level its creator currently holds.
Resourcing lifecycle (FR-28–33)
unresolved

No un-approve path

FR-30, FR-31
An approved candidate later found ineligible has no stated reversal mechanism, leaving headcount permanently marked filled with no correction route.
Fix: allow a DM to reverse an approval to rejected with a written reason, freeing the headcount slot.
unresolved

Headcount editable below filled count

FR-28, FR-31
Nothing blocks editing headcount downward past the already-filled count, making FR-31's "always accurate" guarantee false by construction.
Fix: reject a headcount edit that would drop below the current filled count, or require un-approving first.
unresolved

No cap enforcement at zero remaining

FR-31
FR-31 states the request never auto-closes on the last slot, but nothing blocks approving further candidates once remaining hits zero.
Fix: block new approvals once remaining headcount is zero until the DM raises headcount or closes the request.
unresolved

UM/DM departure mid-decision

FR-29, FR-30, FR-63
A pending proposal or approval decision has no stated reassignment path when the UM/DM owning the next step departs first.
Fix: flag a pending item owned by a now-departed UM/DM for reassignment within the same department/project.
unresolved

Stale routing on UM reassignment

FR-33
A request routed to a department's UM at creation time has no stated behavior if that UM changes before the request is fulfilled.
Fix: routing re-resolves to the department's current UM on every view, not pinned at creation.
Timetracker sync flapping (FR-58)
unresolved

4-hour withdrawal clock resets on any brief recovery

FR-58
A sync that fails, recovers briefly, and fails again repeatedly never accumulates 4 continuous hours, so the withdrawal safeguard may never fire despite far worse cumulative staleness.
Fix: the 4-hour clock accumulates total failed time within a rolling window rather than resetting on any momentary recovery.
unresolved

15-minute grant window has the same flapping gap

FR-58
A genuinely new project assignment observed during a flapping period may never accumulate 15 uninterrupted minutes, so it never registers as an access grant.
Fix: an assignment is confirmed once a single successful sync observes it, not after 15 continuous minutes.
Mentorship consent & concurrency (FR-41–45)
unresolved

No server-side consent gate on pair creation

FR-42
FR-42 relies on browsing the open-to-mentor pool, but nothing states the server rejects creating a pair for someone whose flag is not currently on.
Fix: creating a pair is rejected server-side unless the prospective mentor's flag is currently on.
unresolved

Concurrent pair-ending race

FR-43
Two permission holders ending the same pair at once has no stated resolution; the second closing note could silently overwrite the first.
Fix: reject an end-pair request if the pair's status already transitioned to ended by a concurrent request.
