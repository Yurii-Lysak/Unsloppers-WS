# PRD Quality Review — People Management Platform

## Overall verdict

This PRD is well above the bootcamp-PRD baseline: it has a genuine, load-bearing thesis (per-section, per-audience access control), Success Metrics that validate that thesis rather than measure activity, and a scope-honesty apparatus (Non-Goals, `[NOTE FOR PM]`, Assumptions Index) that is applied — mostly — with discipline. The two real risks are done-ness gaps on a handful of secondary FRs (two literal instances of "handles X gracefully" with no defined behavior) and an inconsistent pattern of flagging `decisions.md`-appendix defaults inline: some FRs (FR-6, FR-29, FR-33) carry a `(Confirmed default — see decisions.md)` annotation and others carrying the exact same kind of appendix-sourced default (FR-19, FR-10, FR-15, FR-32) carry none, which will make it unclear to a developer which behaviors are safe-to-revisit defaults versus settled decisions. Neither issue is disqualifying at Launch-grade stakes, but both are cheap, concrete fixes before this PRD is finalized.

## Decision-readiness — adequate

The PRD states its decisions rather than hedging them: §1's "Confirmed: this is a web application... no native client is in scope" and the `[NOTE FOR PM]` at §6.2 ("these are the first candidates to reintroduce if the team has capacity") are decisions stated as decisions, and the latter is a real tension (a deprioritization call), not a safe checkpoint. §8's "Open Questions: None blocking" reads as earned rather than suspiciously clean, because the grounding SPEC/decisions.md show the resolution work actually happened upstream (D3, D5 confirmed 2026-08-21) rather than being silently swept under a blanket "no open questions."

One real gap: the PRD narrates several SPEC decisions as bare facts, losing the trade-off reasoning a decision-maker would want when re-litigating them later. D6 (`decisions.md`) is explicit that storing mentorship closing-feedback on the pair record rather than in the general Feedback/S8 entity is a "deliberate decoupling" to avoid a cross-developer dependency, with an explicit note to "revisit unifying into S8 later." The PRD's FR-37 states the mechanism ("closing feedback... stored on the pair record itself, not the general Feedback entity") with no signal that this was a trade-off (queryability given up for parallel-delivery independence) rather than a product-driven default. A downstream reader has no way to know this is worth reopening.

### Findings
- **medium** Mentorship-feedback storage trade-off narrated as fact, not decision (§4.9 FR-37) — `decisions.md` D6 frames this as a deliberate trade-off (give up cross-entity queryability to remove a CAP-9→CAP-11 cross-developer dependency) worth revisiting; the PRD states only the resulting mechanism. *Fix:* add a short parenthetical noting the trade-off and that it's revisitable, matching the treatment FR-29/FR-33 give their own defaults.
- **low** D1's caching trade-off is well-surfaced elsewhere (SM-C2 counter-metric explicitly protects cache-invalidation correctness against performance optimization) — flagged here only as a positive example other decisions should be brought up to.

## Substance over theater — strong

No findings of consequence. The Vision (§1) is specific to this platform's actual mechanism ("every piece of information about a person lives in a section... an HR Admin can invent a whole new functional role from the UI on a Tuesday afternoon and have it enforced everywhere by Wednesday") and would not swap cleanly into another PRD in this category — it names the governing idea, not a generic aspiration. The six JTBD personas in §2.1 each map onto a distinct functional role in the access model and each drives specific FRs (HR Admin → FR-5/FR-8, Colleague → FR-3/FR-12); none read as filler. Only two are elaborated into full UJs (Daniela/PP, Marcus/DM), which is restraint, not under-delivery — see Shape fit. There is no differentiation/competitive-novelty section manufacturing unearned innovation claims. The one NFR-shaped line ("External integration failures degrade gracefully," §4.13) is adjective-heavy in isolation but is immediately operationalized by FR-53's fail-safe/fail-soft consequence, so it doesn't read as boilerplate in context.

## Strategic coherence — strong

The PRD runs two theses in parallel and keeps them both legible rather than letting one crowd out the other: the product thesis (strict per-section, per-audience access control replacing "blanket manager sees everything") and the process thesis (parallel, spec-driven delivery is graded above feature count, stated explicitly in §1: "process fidelity as much as working software"). Feature ordering follows the product thesis — §4.1 Access Control is positioned and described as "the platform's core substrate — every other feature depends on it," not first because it's easy. Success Metrics split cleanly along the same two theses: SM-1/SM-2/SM-4 validate the access-model thesis with mechanisms tied to specific FRs ("Validates FR-1, FR-2, FR-3, FR-4"), while SM-5/SM-6 validate the process thesis. Both counter-metrics (SM-C1, SM-C2) are substantive, not filler — SM-C2 in particular names a specific failure mode (a stale permission cache is a data leak, not a performance win) that only makes sense if someone actually thought about how SM-4's optimization work could go wrong. MVP scope (§6.1: all 13 capabilities ship as one delivery, no phased rollout) matches the platform-scope logic that the access-control substrate forces — you cannot ship partial sections against a system whose thesis is that every section needs an enforced rule.

## Done-ness clarity — thin

The load-bearing FRs are specified to a high bar: FR-1–FR-6 (access resolution), FR-42 (campaign activation atomicity), FR-53 (sync fail-safe/fail-soft split), and FR-26/FR-27 (resourcing approval) all carry explicit, verifiable "Consequences (testable)" bullets that an engineer could turn directly into test cases. But roughly half the FRs (FR-10–FR-15, FR-17, FR-21, FR-24–FR-25, FR-27, FR-32, FR-35–FR-36, FR-39–FR-40, FR-47–FR-51) have no Consequences block at all. For most of these the FR statement itself is concrete enough to double as an acceptance criterion (e.g., FR-38's mentor auto-transition fully embeds its own logic), so this is more a texture observation than a blocking gap — but two instances cross into the rubric's explicit red-flag territory:

- FR-45 ("Manager/PP can view an employee's feedback records in chronological order and compare two selected periods side by side, **including handling zero-record periods gracefully**") never says what "gracefully" means: an empty state message, a hidden comparison panel, a zero-count row? This is exactly the "handles X gracefully" pattern the rubric calls out by name, and it's on a comparison UI an engineer will have to build a specific empty state for.
- FR-52 ("Leave data (S10) is pulled from the timetracker's real API") has zero consequence of its own — including no failure-mode behavior — even though decisions.md's D3 and FR-53's own consequence bullet ("S10/S11 display shows 'temporarily unavailable'...") clearly intend S10 to be covered by the same fail-soft rule. An engineer reading FR-52 in isolation would not know leave data has any defined outage behavior at all; it's only discoverable by reading the adjacent FR.

### Findings
- **medium** Undefined "graceful" empty state (§4.11 FR-45, line 311) — "handling zero-record periods gracefully" specifies no behavior. *Fix:* state the actual UI behavior (e.g., "each empty period renders as a zero-count comparison column, not a hidden panel or error").
- **low** FR-52 (Leaves API integration) has no consequence of its own for sync failure, relying on a reader noticing FR-53's consequence covers S10 too. *Fix:* either add a one-line consequence to FR-52 cross-referencing FR-53's fail-soft rule, or fold S10 explicitly into FR-53's scope so the title doesn't undersell it.
- **low** The NFR-shaped line "External integration failures degrade gracefully" (§4.13) is adjective-only in isolation, though it is rescued by FR-53's explicit consequence text elsewhere on the page.

## Scope honesty — adequate

§5 Non-Goals does real work — ten specific exclusions, each with a one-line rationale (e.g., "Compensation and salary data — no compensation section on the profile, this or any planned iteration"), not a vague disclaimer list. §6.2's `[NOTE FOR PM]` on Notifications/Analytics is a genuine deferred-decision flag, not a safe checkpoint. §9's Assumptions Index is honest about its own closure ("All entries below... have since been confirmed... none remain open"), consistent with the Fast-path/batched-assumption authoring mode this PRD was built under.

The gap is consistency, not honesty: `decisions.md`'s Appendix lists eight low-stakes defaults, and the PRD's §8 correctly names all eight in one summary sentence — but only three of them get the inline `(Confirmed default — see decisions.md appendix)` treatment where they actually appear as FR text (FR-6 link expiry, FR-29 soft-delete, FR-33 IDP-reopen-disallowed; plus SM-7's WCAG target makes four). The other four appendix defaults are folded into FR prose with no signal that they're defaults rather than firm decisions:
- FR-19's "even after losing live Manager/PP access to the assignee" is the exact "post-access-loss cancellation" appendix default, stated as flat fact.
- FR-10 (saved views) silently resolves the "static membership list" appendix question by omission — it describes only filter-based views, never mentioning the question existed.
- FR-15 (photo/certificate upload) never mentions the "file constraints" appendix item at all.
- FR-32 (assessment log) never specifies the "assessor field shape" (free text vs. person reference) the appendix flags as needing a pick.

For a PRD feeding three developers building in parallel, this unevenness matters: a developer hitting FR-19 has no cue to check `decisions.md` for whether that behavior is negotiable, while a developer hitting FR-29 does.

### Findings
- **medium** Inconsistent inline flagging of `decisions.md`-appendix defaults (FR-19 vs. FR-29/FR-33 pattern) — four of the eight appendix defaults (post-access-loss cancellation, saved-view shape, upload constraints, assessor field shape) appear in FR text with no default/confirm-if-needed marker, while four others do. *Fix:* apply the same `(Confirmed default — see decisions.md appendix)` annotation FR-29/FR-33 use to FR-19, FR-10, FR-15, and FR-32.

## Downstream usability — strong

This PRD is chain-top (feeds `bmad-ux`, `bmad-architecture`, `bmad-create-epics-and-stories` per §0), so this dimension carries real weight, and it holds up well. The Glossary (§3, 15 terms) is used consistently everywhere it recurs — "Manager line," "Colleague," "Shared Link," "Action item," "Form Campaign" all match their glossary definitions verbatim at every point of use checked (FR-1 through FR-46, the access matrix cross-references, both UJs). Section IDs (S1–S16) are used identically to `access-model.md`'s matrix throughout — UJ-1's "S7 management notes flagged visible-for-PM" and UJ-2's "S1, S4, S12" / "S15" both resolve correctly against the matrix. Internal FR cross-references (e.g., FR-26 → FR-6, FR-41 → FR-7/FR-10, FR-43 → FR-20, FR-46 → FR-40) all point to FRs that exist and match the referenced content. Both UJs have named protagonists (Daniela, Marcus) carrying role and context inline rather than floating.

The one traceability defect — the PRD's own numbering claim not matching its actual FR count — undermines the "stable downstream reference" promise §0 makes; see Mechanical notes.

## Shape fit — strong

This is correctly treated as a multi-stakeholder internal platform, not a single-operator tool — six distinct roles (UM, DM, PM, PP, HR Admin, employee/colleague) with materially different data access, which justifies UJs as load-bearing rather than overhead. The PRD's choice to fully narrate only two UJs (rather than one per persona) is well-calibrated: it grounds the access model in concrete scenarios without padding the document with six formulaic journeys that would mostly restate the access matrix in prose. §4's organization by capability (mirroring SPEC's CAP-1–CAP-13 order exactly) is the right shape for a PRD whose thesis is a substrate every feature depends on — and each feature section carries its own "why," not a bare capability restatement, so it doesn't read as a backlog with headings. Success Metrics are appropriately operational (test coverage, live-API integration, parallel-delivery evidence) rather than forced into user-facing engagement metrics that wouldn't fit an internal tool.

## Mechanical notes

- **FR numbering overstates its own count.** §0 ("FR-1–FR-56") and §6.1 ("All 13 features in §4 (FR-1–FR-56)") both claim 56 functional requirements, but the highest FR actually defined in the document is **FR-55** (§4.13's FR-55, "Resolve cross-system identity"). Counting FRs per feature section (6+6+4+4+3+4+3+4+5+4+3+5+4 = 55) confirms 55, not 56. This is a one-off arithmetic error, but it directly contradicts §0's own claim that FR numbers are "stable downstream reference" — a downstream workflow searching for "FR-56" will not find it. *Fix:* correct both instances to "FR-1–FR-55," or add the missing FR if one was dropped in drafting.
- Glossary drift: none found. Terms are used consistently across FRs, UJs, and the Glossary itself.
- ID continuity: FR IDs are contiguous and non-duplicated (FR-1 through FR-55); all internal FR cross-references checked resolve to real FRs. Section IDs (S1–S16) match `access-model.md` at every checked use.
- Assumptions Index roundtrip: all six §9 entries correspond to inline confirmed-default markers in the document (FR-6, FR-29, FR-33, SM-7, plus §1/§5's web-app-only decision and §2.3's UJ-authorship note). None of §9's entries are orphaned. Note the asymmetry with the scope-honesty finding above: §9 indexes only some of `decisions.md` Appendix's eight defaults — this is a reasonable scoping choice (§8 covers the rest by pointer) rather than a roundtrip failure, since §9 only claims to index what's inline-marked, and everything inline-marked is present.
- UJ protagonist naming: both UJs (Daniela, Marcus) are named with role and context carried inline. No floating UJs.
- Required sections: all present and appropriately weighted for Launch-grade/internal-platform stakes — Document Purpose, Vision, Target User (JTBD + Non-Users + UJs), Glossary, Features/FRs, Non-Goals, MVP Scope, Success Metrics (with counter-metrics), Open Questions, Assumptions Index.
